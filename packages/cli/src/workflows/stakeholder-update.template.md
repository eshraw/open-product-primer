---
name: oprim-stakeholder-update
description: Draft an audience-specific stakeholder update for a period from the boards, objectives and KPI reviews into outputs/ — drafts only, never sends
---

Draft a stakeholder update — what shipped, what we learned, what's next and where we need help — for one audience and one period, from the portfolio's boards, objectives, KPI reviews and bet decisions. The result is a **draft** in `outputs/` for the PM to edit and send themselves.

**Interactive prompts:** Use the **AskUserQuestion tool** for every question in this skill — do not write questions as plain text.

## Hard rules — never break these
- **Never send, post, email, publish or upload anything** — no chat, email, Notion or other external tool calls, even if such tools are available. The only file written is the draft under `outputs/`.
- Every claim about a bet cites its qualified reference: `<source>:BET-NNN` for a product bet, and `<portfolio>:BET-NNN` for a portfolio bet, where `<portfolio>` is this workspace's identity `name` from `.oprim-context/context.yaml` (fall back to the plain `BET-NNN` only if that file is missing). The same for objectives (`OBJ-NNN`) and PDRs.
- Never state a commitment (date, scope, metric target) that is not written in a bet decision, criteria file or review. If the audience needs one that does not exist, write `[TBD — confirm with <owner>]` instead.

## Steps

### 1. Check this is a portfolio workspace
Read `oprim/config.yaml`. If `mode:` is not `portfolio`, stop: "Stakeholder updates run from a portfolio workspace (`oprim init --mode portfolio`)."

### 2. Ask audience and period
Ask, in one AskUserQuestion call:
- **Audience** — `exec`, `eng`, `sales`, `customers` (or another the user types). Use it as a lowercase slug in the filename.
- **Period** — a month (`2027-01`), a quarter (`2027-Q1`), a week (`2027-W03`) or a date range. Default: the current month.

<!-- oprim:portfolio:start -->
### 2b. Ask about assumptions first
Before drafting, ask 2–3 questions about what this audience already believes and needs — what they last heard from you, which decision or worry the update must address, and anything that must not be said yet — and wait for the answers. Shape the draft around them, and list anything left unanswered under `## Open questions` at the end of the draft. (`rules.stakeholder-update.ask_first: false` in `oprim/config.yaml` turns this step off.)
<!-- oprim:portfolio:end -->

### 3. Gather inputs (read-only)
- `oprim ovw --portfolio --json` — boards, delegations, objective coverage, overdue reviews.
- `oprim/objectives/OBJ-*.md` — Active objectives and their key results.
- KPI reviews under each workspace's `oprim/reviews/` — this portfolio's directly, each product's via `oprim context --source <product>` — keeping reviews dated inside the period.
- Bet decisions for every bet mentioned (`## Status`, `## Expected outcomes`, `## Kill criteria`), plus `oprim/bets/archived/` entries archived inside the period (what shipped or was killed).
- `rules.stakeholder-update` in `oprim/config.yaml`: if it is a string, or a map with a `text` key, apply that text as additional guidance.

### 4. Write the draft
Write `outputs/<YYYY-MM-DD>-stakeholder-update-<audience>.md`, where the date is the **last day of the period** (period `2027-01` → `2027-01-31`; for an open-ended period, today). Create `outputs/` if needed. If the file exists, ask before overwriting. Layout:

```
> DRAFT — verify before sending. Generated by /oprim:stakeholder-update from git on <today>; every bet is cited so it can be checked.

# <Audience> update — <period>

## TL;DR
<3 bullets max>

## Outcomes vs objectives
<per Active objective: progress from reviews, with refs>

## Shipped and learned
<archived bets and KPI review verdicts in the period, with refs>

## Now and next
<what is in flight, with refs>

## Risks and asks
<blockers, overdue reviews, decisions needed from this audience>
```

Tune depth to the audience: **exec** — outcomes and asks, no implementation detail; **eng** — dependencies, sequencing and blockers; **sales** — what customers can use and when (only dates written in a bet); **customers** — benefits only, no internal IDs in the prose (keep refs in a final `## Sources` list instead), no unreleased commitments.

### 5. Report
Give the file path, the refs it cites, and any `[TBD …]` placeholders the PM must resolve before sending.
