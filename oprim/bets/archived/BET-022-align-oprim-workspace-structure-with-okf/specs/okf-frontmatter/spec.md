## ADDED Requirements

### Requirement: oprim init SHALL prompt the user to opt in to OKF frontmatter
The `oprim init` command SHALL present an opt-in prompt for OKF (Open Knowledge Format) YAML frontmatter during setup. The feature SHALL be disabled by default — the user must explicitly choose to enable it.

#### Scenario: User opts in during init
- **WHEN** the user runs `oprim init` and answers "y" to the OKF frontmatter opt-in prompt
- **THEN** `oprim/config.yaml` is written with `okf.enabled: true`, the scaffolded `oprim/templates/{bet-decision,pdr,kpi-review}.md` files each include an OKF YAML frontmatter block, and `oprim/index.md` is generated

#### Scenario: User declines during init
- **WHEN** the user runs `oprim init` and answers "n" (or presses Enter) at the OKF frontmatter opt-in prompt
- **THEN** `oprim/config.yaml` is written with `okf.enabled: false`, the scaffolded templates contain no frontmatter, and no `oprim/index.md` is generated

### Requirement: The persisted okf.enabled flag SHALL govern whether skill instructions reference frontmatter
`oprim update` SHALL read the existing `okf.enabled` value from `oprim/config.yaml` and SHALL NOT re-prompt the user. Skill instructions regenerated by `update` SHALL remain consistent with the persisted flag without rewriting already-scaffolded `oprim/templates/*.md` files.

#### Scenario: Update preserves an existing opt-in
- **WHEN** the user runs `oprim update` on a project where `oprim/config.yaml` has `okf.enabled: true`
- **THEN** the update completes without prompting for OKF frontmatter and does not modify the existing `oprim/templates/*.md` files

#### Scenario: Update preserves an existing opt-out
- **WHEN** the user runs `oprim update` on a project where `oprim/config.yaml` has `okf.enabled: false` or the field is absent
- **THEN** the update completes without prompting for OKF frontmatter and no frontmatter-related files are generated or modified

### Requirement: The system SHALL generate an oprim/index.md OKF bundle entrypoint when enabled
When OKF frontmatter is enabled at `oprim init` time, the system SHALL write `oprim/index.md` with OKF-compliant frontmatter (`type: index`) and a body linking to the `bets/`, `decisions/`, and `reviews/` directories.

#### Scenario: index.md created on opt-in
- **WHEN** a user opts in to OKF frontmatter during `oprim init`
- **THEN** `oprim/index.md` is created containing `type: index` frontmatter and links to `oprim/bets/`, `oprim/decisions/`, and `oprim/reviews/`

#### Scenario: index.md not created when opted out
- **WHEN** a user does not opt in to OKF frontmatter during `oprim init`
- **THEN** no `oprim/index.md` file is created

### Requirement: OKF frontmatter blocks SHALL contain type, title, description, tags, and timestamp fields
Each generated frontmatter block SHALL include the OKF fields `type`, `title`, `description`, `tags`, and `timestamp`, with `type` set to the artifact's kind (`bet-decision`, `pdr`, or `kpi-review`).

#### Scenario: Frontmatter fields present on a scaffolded bet-decision template
- **WHEN** OKF frontmatter is enabled and a user scaffolds `oprim/templates/bet-decision.md` via `oprim init`
- **THEN** the file's frontmatter block contains `type: bet-decision`, and placeholders for `title`, `description`, `tags`, and `timestamp`

### Requirement: criteria.yaml SHALL remain out of scope for OKF frontmatter
The system SHALL NOT add OKF frontmatter to `oprim/templates/criteria.yaml` or any generated `criteria.yaml` file, regardless of the opt-in state.

#### Scenario: criteria.yaml unaffected by opt-in
- **WHEN** OKF frontmatter is enabled during `oprim init`
- **THEN** `oprim/templates/criteria.yaml` is written exactly as it is today, with no frontmatter block added
